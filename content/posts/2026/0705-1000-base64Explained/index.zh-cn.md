Base64 无处不在：CSS 里的 data URI、JWT 的各段、邮件附件、API 载荷、`kubectl get secret` 的输出。它属于那种人人在用、却很少有人能精确讲清的东西。本文讲清它的原理、存在的意义，以及两个真会引发 bug 的误解。

<!--more-->

### Base64 解决的问题

很多系统当初是为传输**文本**设计的，而不是任意字节。邮件（SMTP）、早期 HTTP 头、JSON、XML、URL——这些通道历史上会破坏或卡在原始二进制上：空字节、控制字符、大于 127 的字节。Base64 用一招绕开了整个问题：把**任意**二进制数据重新编码为仅 64 个"安全"的可打印 ASCII 字符，这些字符能原封不动地穿过上述通道。

所以 Base64 是一种**传输编码**。它的职责就是让二进制数据"文本安全"——仅此而已。

### 工作原理

Base64 每次处理**3 个字节**。3 字节 = 24 位。这 24 位被重新切成**四个 6 位一组**，每个 6 位组（取值 0–63）映射到字母表里的一个字符：

```
输入字节:   M           a           n
ASCII:      77          97          110
二进制:     01001101    01100001    01101110
重新分组:   010011  010110  000101  101110
数值:       19      22      5       46
Base64:     T       W       F       u
```

于是 `Man` → `TWFu`。标准字母表是 `A–Z`、`a–z`、`0–9`、`+`、`/`。

当输入不是 3 字节的整数倍时，Base64 用 `=` 补齐，使长度始终是 4 的倍数。剩 1 个字节 → 两个字符 + `==`；剩 2 个字节 → 三个字符 + `=`。

### 为什么体积会大约 33%

每 3 字节（24 位）变成 4 个字符（每个字符只承载 6 个有效位）。这是 4:3 的比例——补齐之前就是 **33% 的体积膨胀**。这一点很重要：把一张 1 MB 的图片做成 data URI，会在你的 HTML/CSS 里变成约 1.37 MB 的文本。用在小图标上没问题，用在大文件上就是浪费。

### 标准字母表 vs URL 安全字母表

标准字母表用 `+` 和 `/`，但这两个在 URL 里都有特殊含义（`/` 是路径分隔符，`+` 在查询串里可能被解码成空格）。于是有了 **URL 安全**变体（RFC 4648 §5），把它们替换掉：

- `+` → `-`
- `/` → `_`

JWT 用的是**不带补齐**的 URL 安全 Base64。如果你用严格的标准 Base64 解码器去解 JWT 的某一段，可能会因为缺少 `=` 或出现 `-`/`_` 而失败。当某个东西"死活解不出来"时，字母表不匹配通常就是元凶。

### 两个会引发 bug 的误解

**1. "Base64 是加密／能藏住我的数据。"** 并不能。Base64 完全可逆、无需任何密钥，谁都能解。把密码或 API key 做成 Base64，安全性和明文写出来一模一样——甚至更糟，因为它*看起来*被遮住了，反而让人放松警惕。比如 Kubernetes 的 Secret 是 Base64 编码而非加密，这正是集群 RBAC（以及静态加密）之所以重要的原因。Base64 用于传输，绝不用于保护。

**2. "Base64 会自动处理 Unicode。"** Base64 编码的是**字节**，不是字符。要对 `café` 这样的字符串做 Base64，你得先用某种字符编码把它变成字节——几乎总是 UTF-8。跳过这一步（或用错编码），另一端就会得到乱码。浏览器里老的 `btoa()` 遇到非 Latin1 字符会直接抛错，原因正是这个；你必须先做 UTF-8 编码。

### Base64 是正确工具的场景

- 把小资源（图标、字体）以 `data:` URI 内嵌，省掉一次请求
- 在只接受字符串的 JSON/XML 字段里编码二进制
- 邮件 MIME 附件
- 安全地在 URL 或 HTTP 头里编码原始字节

以及它不合适的场景：大文件（33% 的开销 + 无法流式处理），或任何你以为"需要藏起来"的东西。

### 小结

- Base64 是传输编码：二进制 → 文本安全，体积大约 +33%。
- 它**不是**加密。无密钥、完全可逆。
- 先把文本编码成字节（UTF-8）*再*做 Base64。
- 注意字母表：标准 vs URL 安全，带补齐 vs 不带。
