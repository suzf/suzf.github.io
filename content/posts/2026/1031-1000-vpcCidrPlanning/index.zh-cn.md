CIDR 网段是创建 VPC 时最先填的东西，也是之后最难改的东西之一。控制台建议 `10.0.0.0/16`，你就用了；下一个账号也这么用。一年后这两个 VPC 无法对等连接，通往办公室的 VPN 有一半流量被路由进了错误的网络，唯一真正的解决办法是重建其中一个。

这篇文章是我用来避免这种情况的流程：先盘点已经在用的网段，自上而下切分私有地址空间，按实际要承载的东西估算每个 VPC 的大小，按可用区划分子网，并在创建任何东西之前把整份清单检查一遍是否有重叠。示例以 AWS 为主，Azure 和 Google Cloud 有差异的地方会单独说明。

<!--more-->

## 1. 为什么第一次的选择很难改

在 AWS 上，VPC 的主 CIDR 创建后不能修改。你可以关联辅助网段（默认每个 VPC 最多 5 个，而且哪些网段能组合有规则限制），而子网根本不能调整大小：想变大只能新建一个子网，把东西全部迁过去。Google Cloud 允许扩大子网的主网段，但不能缩小；Azure 允许给 VNet 添加地址范围。但这些都解决不了真正的问题：两个网络用了相同的地址。

重叠之所以致命，是因为路由按目的地址转发。一张路由表对 `10.0.5.20` 只能有一个去向。如果两个网络都包含这个地址，任何需要同时访问这两个网络的东西都会出问题：

- **VPC 对等连接**会直接拒绝连接 CIDR 相同或重叠的 VPC。
- **Transit Gateway 和 VPN** 对同一个地址范围只能承载一条路由，其中一个网络就从其他地方访问不到了。
- **主机和容器**会把流量发往本地路由更优先的那个网络。`172.17.0.0/16` 上的 Docker 网桥会悄无声息地截走本该发往 `172.16.0.0/12` 合作方网络的流量。

这种问题第一天很少暴露。它出现在两个团队、两次收购或两朵云需要互通的时候，而那时两个网络里都已经跑满了业务。

## 2. 先盘点已经被占用的网段

在选新网段之前，先把已经存在的、以及各种工具会不打招呼就创建的网段全部列出来。我的清单通常是这样的：

- 所有账号、订阅和项目里现有的 VPC 和 VNet；
- 办公室、数据中心以及客户端 VPN 地址池；
- 通过 VPN 或专线连接的合作方、供应商网络；
- 容器默认网段：Docker 的 `172.17.0.0/16` 网桥，以及它给自定义网络用的地址池（继续占用 `172.16.0.0/12` 里的网段，然后是 `192.168.0.0/16`）；
- Kubernetes 网段：kubeadm 默认的 Service 网段 `10.96.0.0/12`、Flannel 的 `10.244.0.0/16`、Calico 的 `192.168.0.0/16`，以及 EKS 的 Service 网段（不指定时为 `10.100.0.0/16` 或 `172.20.0.0/16`）；
- Tailscale 这类覆盖网络，它使用 `100.64.0.0/10`；
- 连 VPN 的同事家里的网络，几乎都是 `192.168.0.0/24` 或 `192.168.1.0/24`。

最后几项就是我把云上网络都放在 `10.0.0.0/8` 里、把 `172.16.0.0/12` 和 `192.168.0.0/16` 留给工具和家用路由器的原因。这两段是软件最爱选的默认值，所以也最容易撞车。

## 3. 自上而下切分私有网段

`10.0.0.0/8` 有 16,777,216 个地址。听上去很多，可一旦大家随手拿 `/16`，很快就乱了。所以先给地址空间定一个结构，再从里面分配。我用得比较顺的一种布局是：每个地域一个 `/12`，地域内每个环境一个 `/16`。

```
10.0.0.0/8        整个组织
  10.0.0.0/12       us-east-1         10.0.0.0  - 10.15.255.255
    10.0.0.0/16       prod
    10.1.0.0/16       staging
    10.2.0.0/16       dev
    10.3.0.0/16 …     还有 13 个 /16 留给新账号
  10.16.0.0/12      eu-west-1         10.16.0.0 - 10.31.255.255
  10.32.0.0/12      ap-southeast-1
  …
  10.240.0.0/12     办公室、数据中心、客户端 VPN
```

`10.0.0.0/8` 能切成 16 个 `/12`，每个 `/12` 又能切成 16 个 `/16`，所以这个方案最多支持 16 个地域、每个地域 16 个 VPC。层级可以按你的情况调整（按业务线、按账号、按云厂商），但要守住一条规则：每个网段都在它的父网段之内，规划之外不分配任何东西。

回报是**汇总路由**。eu-west-1 的所有东西都在 `10.16.0.0/12` 里，VPN 或 Transit Gateway 只需要一条路由就能到达整个地域，而不用每个 VPC 一条；防火墙规则也能用一行写出"来自 eu-west-1 的所有流量"。前提是网段要对齐：`10.0.0.0/16` 和 `10.1.0.0/16` 可以汇总成 `10.0.0.0/15`，但再加上 `10.2.0.0/16` 就又需要两条路由了（`10.0.0.0/15` 和 `10.2.0.0/16`），因为一个 CIDR 网段覆盖的地址数总是 2 的幂，而且起点必须是自身大小的整数倍。

布局时注意两点：

- 如果你用 kubeadm 默认 Service 网段建集群，每个集群内部都占用了 `10.96.0.0/12`。要么把这个 `/12` 从规划里剔除，要么把 `--service-cidr` 设成规划内分配给它的网段。
- 用一张表格、一个 IPAM 工具（AWS VPC IPAM、NetBox）或 Git 里的一个文件作为唯一的分配记录。规划好不好，取决于记录准不准。

## 4. 按实际承载估算 VPC 大小

AWS 上 VPC 的大小可以从 `/16`（65,536 个地址）到 `/28`（16 个）。只要是要跑业务的 VPC，我默认给一个完整的 `/16`：私有地址不花钱，而 VPC 不够用时无法原地扩容。

最大的消耗方通常是 Kubernetes。EKS 上使用 Amazon VPC CNI 时，不只是每个节点，每个 Pod 都会从子网拿一个真实地址。50 个节点、每个节点跑 30 个 Pod，就需要 1,500 个 Pod 地址，还没算同一子网里的节点、负载均衡器和终端节点；而且每次有人调高 `maxPods` 或加节点组，这个数字都会涨。开启前缀委派后，CNI 给每个节点分配的是 `/28` 块，所以子网里还得有空闲且连续的 `/28`，零散的单个地址再多也不行。

如果 VPC 已经不够用，AWS 上常见的出路是从 `100.64.0.0/10` 里拿一个辅助网段专门给 Pod 用（EKS 的"自定义网络"）。这些地址不会被路由到 VPC 之外，所以每个 VPC 都可以重复使用而不会造成重叠，可路由的 `10.x` 网段则留给需要从外部访问的东西。

只有当网络确实只承担固定的小任务时，才适合用小 VPC，比如 VPN 中转或流量检测 VPC。这类可以给 `/24` 或 `/22`，但依然要在规划之内。

## 5. 按可用区划分子网

在 VPC 内部，给每一层（公有、私有、数据）一个连续的网段，每层里每个可用区一个子网。先分配最大的网段，这样才能保持对齐；每一层都给第四个可用区留出位置。下面是按这种方式规划的 `10.0.0.0/16`：

```
10.0.0.0/17     私有层（32,768）
  10.0.0.0/19     private-a     AWS 中可用 8,187
  10.0.32.0/19    private-b     8,187
  10.0.64.0/19    private-c     8,187
  10.0.96.0/19    （预留：第四个可用区）
10.0.128.0/21   公有层
  10.0.128.0/24   public-a      251
  10.0.129.0/24   public-b      251
  10.0.130.0/24   public-c      251
10.0.136.0/21   数据层
  10.0.136.0/24   data-a        251
  10.0.137.0/24   data-b        251
  10.0.138.0/24   data-c        251
10.0.144.0/20、10.0.160.0/19、10.0.192.0/18   未分配
```

私有子网大，是因为节点和 Pod 都在里面。公有子网只放负载均衡器和 NAT 网关，数据子网放数据库和缓存，各给一个 `/24` 足够了。因为每一层都是一个对齐的网段，安全组或网络 ACL 可以直接用 `10.0.0.0/17` 表示"所有私有子网"。

九个子网都建好后，65,536 个地址里还剩 39,424 个空闲，分成八块：`10.0.96.0/19`、`10.0.131.0/24`、`10.0.132.0/22`、`10.0.139.0/24`、`10.0.140.0/22`、`10.0.144.0/20`、`10.0.160.0/19` 和 `10.0.192.0/18`。以后加第四个可用区、终端节点子网或新的一层，都从这里出。

在 Terraform 里，用 `cidrsubnet(prefix, newbits, netnum)` 从 VPC 网段计算子网，而不是手写。`newbits` 是前缀长度要增加的位数，`netnum` 是取切分结果中的第几块：

```hcl
locals {
  vpc_cidr = "10.0.0.0/16"
  azs      = ["us-east-1a", "us-east-1b", "us-east-1c"]

  # /16 加 3 位 = /19：10.0.0.0/19、10.0.32.0/19、10.0.64.0/19
  private = [for i, az in local.azs : cidrsubnet(local.vpc_cidr, 3, i)]
  # /16 加 8 位 = /24，从第 128 块开始：10.0.128.0/24、10.0.129.0/24、10.0.130.0/24
  public  = [for i, az in local.azs : cidrsubnet(local.vpc_cidr, 8, 128 + i)]
  # 从第 136 块开始：10.0.136.0/24、10.0.137.0/24、10.0.138.0/24
  data    = [for i, az in local.azs : cidrsubnet(local.vpc_cidr, 8, 136 + i)]
}
```

每个可用区的 `netnum` 要固定。如果子网是根据列表的*长度*算出来的，有人从中间删掉一个可用区，后面每个子网的 CIDR 都会变，Terraform 就会计划替换它们，连同里面的所有资源。

## 6. 各家云的保留地址和最小子网

每家云都会在每个子网里为自己保留几个地址，所以可用数量比教科书上的"总数减 2"更少：

| | 每个子网保留 | `/24` 可用 | 最小 IPv4 子网 |
|---|---|---|---|
| AWS | 5 个：前四个和最后一个 | 251 | `/28`（可用 11） |
| Azure | 5 个：前四个和最后一个 | 251 | `/29` |
| Google Cloud | 4 个：前两个、倒数第二个和最后一个 | 252 | `/29` |

有些托管服务还要求子网有固定的大小或名称。Azure 上 `AzureFirewallSubnet` 和 `AzureBastionSubnet` 需要 `/26` 或更大，`GatewaySubnet` 至少应为 `/27`。这些网段要和其他网段一起规划，而不是最后塞进剩下的空隙里。

## 7. 创建前先检查重叠

不管规划在脑子里还是在表格里，都需要和实际情况对一遍，尤其是清单里有其他团队负责的网络时。把所有需要互通的网段放进同一份清单，检查有没有重叠。下面是一份很真实的清单：两个地域、一个有人从控制台随手建的沙箱 VPC、办公室 VPN、一个 EKS 集群的 Service 网段、Docker 网桥和一个合作方网络。

```
use1-prod         10.0.0.0/16
use1-staging      10.1.0.0/16
euw1-prod         10.16.0.0/16
euw1-sandbox      10.0.0.0/16
office-vpn        10.240.0.0/16
eks-services      172.20.0.0/16
docker-bridge     172.17.0.0/16
partner-network   172.16.0.0/12
```

有三个问题：

```
use1-prod 10.0.0.0/16        与   euw1-sandbox 10.0.0.0/16      完全相同
eks-services 172.20.0.0/16   在   partner-network 172.16.0.0/12 之内
docker-bridge 172.17.0.0/16  在   partner-network 172.16.0.0/12 之内
```

第一个是控制台默认值的老毛病（有些团队正因为这个，从不分配 `10.0.0.0/16`）。另外两个是落在 `172.16.0.0/12` 里的工具默认值：EKS 集群和 Docker 主机都无法访问合作方网络中被自己网段覆盖的那部分。

手工检查很容易出错，因为大小不同的网段会互相"藏住"：`172.17.0.0/16` *看起来*和 `172.16.0.0/12` 没关系。两个 CIDR 网段要么完全不重叠，要么一个完全包含另一个，所以检查是机械性的。我做了一个免费的 [CIDR 子网计算与重叠检查工具](https://suzf.net/zh/tools/cidr-calculator)：把清单粘进去（可以带标签和 `#` 注释），它会列出所有重复和嵌套的网段，并给出整组网段的汇总路由。填上一个父网段（比如 VPC 网段），它就把清单当作这个 VPC 的子网：重叠标记为冲突，超出父网段的单独标出，剩余空间以可以直接使用的 CIDR 网段列出——第 5 节里的空闲网段就是这样得到的。所有计算都在浏览器里完成。

## 8. 已经重叠了怎么办

唯一彻底的办法是给其中一个网络重新编址，而这是一次迁移，不是改个配置。在下决心之前，下面这些方法可以和重叠共存，按工作量从小到大排列：

- **改工具，不改网络。** Docker 的网段可以在 `/etc/docker/daemon.json` 里配置（`bip` 设置默认网桥，`default-address-pools` 设置它创建的网络），Kubernetes 的 Service 和 Pod 网段在建集群时指定。和重新编址一个 VPC 比，改这些成本很低。
- **暴露服务，而不是暴露网络。** 如果重叠的网络之间只需要访问少数几个服务，可以用 AWS PrivateLink（Google Cloud 的 Private Service Connect、Azure 的 Private Link）把一个终端节点发布到另一个 VPC 里，两边的地址根本不需要互相可路由。
- **地址转换。** 在一个不重叠的"中转"网段里放一个私有 NAT 网关，重叠的 VPC 访问其他网络时就像是从这个网段发出的。这能用，但所有流量都要经过 NAT，而且对端网络无法主动发起连接。
- **重新编址。** 按规划新建一个 VPC，把业务迁过去（或用 Terraform 重建），然后删掉旧的。有了规划，至少这件事只用做一次。

## 9. IPv6 呢？

IPv6 基本上消除了这个问题：AWS VPC 会从 Amazon 的地址池拿到一个全局唯一的 `/56`，可以容纳 256 个 `/64` 子网，两个 VPC 永远不会冲突。但大多数环境仍是双栈，IPv4 这一侧上面的问题一个都不少。即使要加 IPv6，IPv4 也要认真规划；IPv6 每个子网直接给 `/64`，就不必再考虑子网大小了。

## 10. 检查清单

- 把在用的网段全部记下来，包括 Docker、Kubernetes、VPN 地址池和合作方网络。
- 云上网络放在 `10.0.0.0/8`；把 `172.16.0.0/12` 和 `192.168.0.0/16` 留给工具和家用路由器。
- 按有记录的规划自上而下分配：每个地域一个网段，每个 VPC 一个 `/16`。
- 按 Pod 而不只是节点来估算 VPC 大小，每一层都预留一个可用区。
- 用 `cidrsubnet()` 和固定的索引计算子网。
- 记住保留地址：AWS 和 Azure 每个子网 5 个，Google Cloud 4 个。
- 在创建或对等连接任何东西之前，先检查整份清单有没有重叠。
